# Camera and FastRPC driver entry accounting

This is the first source-integrated change toward the
[ownership transaction](QUEST2_OWNER_AUDIT.md#driver-ownership-implementation-boundary)
for Hollywood firmware `52242990024200150`. **It implements annotated entry and
lifetime accounting, not complete resource ownership or checked shutdown.**
The stock headset's built-in drivers have not been replaced by this source patch.

The subsequent [resource-lifetime work](QUEST2_RESOURCE_LIFETIMES.md) adds selected
failure-preserving cleanup under the same default-off option and records the
exact installed bootloader gate. Its enabled option now includes those cleanup
changes; the first-build evidence below remains a historical checkpoint.

## Source changes

The source applier verifies whole-file, exact signature and complete-function
hashes against kernel commit `6bde5fc06b252c97761bc0963dd13c1abcf377ab` before
preparing any writes. It inserts wrappers at 150 sites across 36 driver files:

| Domain | Sites | Reject new entry when fenced | Observe without rejecting |
| --- | ---: | ---: | ---: |
| Camera | 119 | 50 | 69 |
| FastRPC | 31 | 2 | 29 |

Camera coverage includes CRM, generic and fastpath subdevices, sensor/CSIPHY,
CCI, CPAS, camera-sync, the fastpath queue device and selected kernel memory
entry points and callbacks. FastRPC coverage includes open/native ioctl,
release/destruction, procfs/sysfs accounting, RPMsg/notifier and selected
invocation/mapping paths. Compat forwarding reaches the instrumented native
entry where verified. The pinned manifests list each individual site.

The applier keeps the original signature, return value, conditional scope and
function-body bytes. A wrapper calls the original body and then leaves its
accounting entry. New core/header files and the `QKX_OWNER_GATE` Kconfig option
are installed separately. The option defaults to **off**, with inline no-op
entry/leave helpers and an unsupported snapshot query when disabled.

```sh
python3 -B tools/quest2_apply_owner_gate.py \
  --source /absolute/disposable/verified-kernel \
  --receipt /absolute/private/new-owner-receipt.json
```

Use a quiescent disposable source tree. Every input is checked and all outputs
prepared before writes begin. Replacements are atomic per file; a partial
failure leaves an incomplete marker. This is not an atomic tree-wide update or
a concurrent-editor protocol. Do not compile a partially applied tree. The
receipt records original and generated byte counts/hashes and false deployment
and full-ownership fields. This tool never connects to a headset.

## Accounting contract

The shared core tracks active submission/lifecycle entries and a monotonically
advancing epoch under a short spinlock. It samples its monotonic clock while
holding that lock, avoiding stale pre-lock timestamps being misread as clock
rollback. A private fence refuses acquisition while entries are active; it does
not wait for potentially unbounded driver invocations. Its lease is at most
100 ms and expires on the next core operation.

Completion, close and lifecycle entries always execute. They invalidate a
previously stable entry fence. Clock rollback, counter/epoch exhaustion and
deadline overflow poison accounting so no valid fence can be asserted. An old
fence cannot reopen a later one. These checks cannot bound a stalled CPU or
kernel primitive and do not pin any camera/DSP object between calls.

Only the snapshot query is exported by a patched kernel; it also performs
expired-lease maintenance. **No module-facing fence or drain controller is
exported.** A monolithic ioctl gate would also reject userspace STOP/UNMAP;
the future owner-control bypass and checked retirement protocol remain work.

## Test boundary

Host tests execute the production core with lock/clock doubles, including
15 shared state-machine cases and a separate disabled-option compilation.
The source-applier tests compile synthetic wrappers to check result preservation,
conditional scope, rejection and always-running lifecycle behavior. All 150 real
source sites have passed hash/signature/lexical application checks.

`module/owner_gate_selftest.c` embeds the production core into its **own
unexported module state**, using real kernel spinlocks and a controlled test
clock. It has no stock driver bindings, probes, ioctls, MMIO or handoff code.
It requires explicit `observe=1` and the matching Hollywood kernel/model. Its
15 passing cases validate this isolated accounting implementation, not camera
or FastRPC execution, real-time behavior, pending work or hardware ownership.

The matching-loader workflow's optional `owner_gate=true` build first builds
and audits that module against the unchanged stock configuration. It then
applies the source patch and compiles the modified kernel with the option off
and on. Stock-module ABI evidence and modified-kernel provenance are separate.
The artifact contains the generated source patch, logs and hashes; no installable
Horizon boot image is exported.

The unchanged matching kernel and baseline modules passed their existing ABI

The downloaded 28-file artifact matched GitHub's archive digest and every
`SHA256SUMS` entry. Its source receipt matched the independently reproduced
receipt, and all five modules passed an independent ELF/vermagic/import audit.
The isolated self-test module is 90,968 bytes, SHA-256
`cadab91d5365aefcce7bb878d383565cb360774ef9fb2ef1e6aa7c166b9ee361`.
All 14 version records match generated and observed stock export CRCs. The
module exports no controls and imports no camera/FastRPC or probe interface.

On the matching rooted Quest 2, one explicit module insertion produced:

```text
QKX_OWNER_SELFTEST cases=15 result=PASS driver_bindings=0 controlled_clock=1
```

The module unloaded and its sole temporary file was removed. Boot identity,
CPU set, stock module names, panic/watchdog settings and sampled DSP, camera,

The strict capture flagged a taint change from **1028 to 5124**. The only added

evidence was retained; a separate assessment records this explained delta.
The test was not repeated and did not reboot or change the built-in drivers.
Raw captures and device identifiers remain private. **Actual patched-driver
execution, retained resource ownership and hardware shutdown remain unvalidated.**

## Running modified Horizon drivers

The verified current configuration builds camera/FastRPC into Horizon. Ordinary
module loading cannot replace them. No route to run all patched built-ins on
this exact unit has been validated:

- RAM boot through fastboot requires this bootloader's command and image
  acceptance policy to be established. The locked-state report alone does not
  settle every implementation-specific behavior. See the [AOSP protocol](https://android.googlesource.com/platform/system/core/+/master/fastboot/README.md).
- Changed signed boot-image bytes need an accepted verification path; retaining
  the old signature is insufficient. See [AVB verification](https://android.googlesource.com/platform/external/avb/+/master/README.md).
- Temporary kexec into modified Horizon remains a research path requiring the
  existing RAM, DMA shutdown, ARM64 entry, boot-asset and independent recovery
  prerequisites. Success reported by upstream on another build does not validate
  this headset. See the [upstream Quest 2 port](https://github.com/machachu56/quest-kexec-q2/tree/quest2-port).
- Supported livepatch is absent in the observed configuration. Kprobe PC
  redirection is not an equivalent consistency protocol: the pinned ARM64
  [reentry path](https://github.com/facebookincubator/oculus-linux-kernel/blob/6bde5fc06b252c97761bc0963dd13c1abcf377ab/arch/arm64/kernel/probes/kprobes.c#L283)
  can increment a miss and single-step the original instruction without running
  the admission handler. An enabled kprobe facility cannot establish a complete
  fail-closed replacement by itself.

Pending work includes retained object/generation identities, all asynchronous
and hard-IRQ paths, callback registration and between-call work lifetimes,
debugfs/sysfs/probe/remove coverage, owner-issued drain operations, original
release errors, secure-memory retirement, DSP-loader references and a validated
deployment/recovery path. The Hollywood hardware handoff gate remains closed.
